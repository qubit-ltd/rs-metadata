## 问题与证据

| crate | 当前路径 | 保留的版本要求 | 保留的配置 |
| --- | --- | --- | --- |
| qubit-datatype | ../rs-datatype | ^0.15 | default-features = false；converter |
| qubit-json | ../rs-json | ^0.12 | optional = true |
| qubit-redact | ../rs-redact | ^0.10 | default-features = false |
| qubit-value | ../rs-value | ^0.13 | default-features = false；converter、redact |

版本要求不会在路径不存在时自动替代路径来源。当前开发目录恰好包含这些仓库，单独检出 rs-metadata 的环境则缺少相应 Cargo.toml。

## 目标与持续适用的约束

成功标准是在没有 rs-* 兄弟目录、没有本地 path patch 的环境中，当前 crate 可以完成依赖解析，并通过自己的既有验证。

持续遵循用户要求：

- 使用当前 Paseo workspace，不创建或打开新的 Paseo workspace。实施验收所需的可丢弃隔离目录仅用于文件快照和命令运行，不注册为 Paseo workspace。
- CI 只验证当前 crate 自身，不加入或保留 downstream all-features 测试。
- 只修改任务直接相关内容，不顺手重构、格式化或清理；优先采用满足目标的最小改动。
- 保留实施开始时已有的用户工作；不得将其静默覆盖或归入本修复。删除、移动或提交等操作仍依据实施阶段的明确授权及适用仓库规则处理。

## 方案选择

采用版本依赖：仅移除四条依赖中的 `path` 字段，保留版本、默认 feature 设置、显式 feature 和 optional 状态。正常检出从注册表解析依赖，锁文件保存选定版本和校验信息。

与“补齐兄弟仓库并固定 revision”的方案相比，这不需要改变受管配置、引入基础设施定制或维护跨仓库检出闭包。与新增 Git 依赖相比，它沿用已有发布版本契约。当前不重构依赖管理体系。

实施后的四条声明为：

```toml
qubit-datatype = { version = "^0.15", default-features = false, features = ["converter"] }
qubit-json = { version = "^0.12", optional = true }
qubit-redact = { version = "^0.10", default-features = false }
qubit-value = { version = "^0.13", default-features = false, features = ["converter", "redact"] }
```

`Cargo.lock` 与 `fuzz/Cargo.lock` 已被跟踪，需要按 Cargo 实际解析结果同步来源、校验信息和必要的传递依赖变化。不得手工捏造 checksum，也不执行无差别依赖升级。`fuzz/Cargo.toml` 中 `qubit-metadata = { path = "..", ... }` 指向本仓库父目录，属于仓库内部关系，应保留。

实施前先核实既有版本区间内的已发布包及所需 feature 可用。若已发布包缺失或接口与当前源码不兼容，应记录具体包、版本和错误，停止该实施路径；不得为完成本项自动发布依赖、升级版本区间、改写业务 API 或修改兄弟仓库。该条件是方案可行性的实施核查，不是重新打开用户已确认的采纳范围。

## 变更边界与兼容性

预期修改范围仅为 `Cargo.toml`、`Cargo.lock` 和 `fuzz/Cargo.lock`。不修改生产 Rust 源码、测试语义、feature 定义、MSRV、V1 wire 协议、公共 API、README 或既有设计文档；不修改 `.infra` 文件和共享 workflow。当前安装说明已经使用注册表版本依赖，不需要为本修复重写中英文文档。

不设计破坏性 API 变更，下游调用点无需迁移。实际变化是本地联调不再自动读取兄弟目录的未发布修改；确需联调的开发者可在应用根或仓库外 Cargo 配置中显式使用 `[patch.crates-io]`。该覆盖由开发者自行选择，不能成为正常构建、CI 或本轮验收的前置条件，也不在本次修复中创建覆盖配置。

## 验证设计

验证对象是依赖解析边界，现有干净 CI runner 已可充当回归检查，无须增加仅镜像 Cargo.toml 的 Rust 测试。

1. 实施前保存当前文件状态，制作当前工作树内容的独立快照。不能直接使用 `git archive HEAD` 而遗漏已有暂存改动；不复制 `.git`、target、缓存和本地 Cargo 覆盖。快照父目录没有四个兄弟目录。在该环境执行 Cargo metadata，记录缺失路径的基线错误。
2. 修改依赖并同步两个锁文件后，重新制作同等隔离快照。在无额外 Cargo patch 或 source 替换的受控配置下，运行根 crate 的 `cargo metadata --locked --all-features --format-version 1`，以及 fuzz manifest 的锁定解析。确认四个包均来自注册表，只有本项目及 fuzz 到本项目的仓库内关系使用本地路径。
3. 在同一干净快照中执行一次当前 crate 的既有 CI 入口 `./.infra/bin/ci-check.sh`，由其负责既有 feature 矩阵、Clippy、文档及 fuzz 等配置内检查。不得另行运行下游测试，也不重复手工跑完整矩阵。依赖准备清单仍为空，但构建不再需要兄弟源码目录。
4. 查看最终 diff，确认只含四个 path 删除及两个锁文件中必要的解析变化；既有暂存修改保持原样。若某个锁文件不需要变化，则保留原内容。

注册表、网络或工具安装失败应与缺失本地路径分别记录，不能把网络失败当作修复验证成功。若既有 CI 出现与本修复无关的失败，保留具体证据，不扩大修改范围，也不宣称全部通过。

## 验收与风险

验收须同时满足：独立快照无兄弟目录；四个依赖从注册表按原版本区间解析；两份锁文件可用 `--locked`；当前 crate 的既有 CI 通过；无下游 all-features 测试；最终变更范围可解释且不覆盖用户工作。

主要风险是已发布依赖与本地候选代码的差异。通过实施前版本/feature 核实和干净环境构建识别，不能用本地 patch 掩盖。另一风险是锁文件解析造成无关升级，应审阅版本与来源 diff，优先保留已有可用版本，仅接受解算所必需的变化。

若方案不可行，保留失败证据后再提出针对 RSMD-001 的替代路径；不要恢复成仅在开发机可用的隐式路径依赖后声称修复完成。任何回退只撤销本次实施产生的变更，不重置已有用户内容。
